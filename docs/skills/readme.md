# Skills 技能编排

> 本文档 AI + 社区共建中

## 为什么 Skills 值得学

先不讲定义，看三个场景。

**场景一：部署到生产环境**

你在 Claude Code 里输入 `/deploy`，它自动帮你跑 lint、跑类型检查、构建项目、部署到 Vercel、检查线上是否正常。整个过程你只说了一个词。

**场景二：代码审查**

你输入 `/review`，它自动 diff 当前分支和 main 的差异，按团队规范逐项审查——SQL 注入风险、类型安全、错误处理、命名规范、测试覆盖率，最后输出一份结构化报告。

**场景三：科学实验流程管理**

你是一个做 AGI4S（AI for Science）的研究者，输入 `/experiment`，它自动检查 GPU 可用性、确认数据集完整性、验证环境依赖、记录实验参数、启动训练，训练完成后自动对比基线结果。

这三个场景有一个共同点：**它们不是一个单独的操作，而是一套完整的流程**。每次手动执行要记住十几个步骤，漏掉一步就可能翻车。

Skills 解决的问题就是：**把你脑子里的操作流程，变成 AI 能读懂、能执行的标准化文档**。你写一次，以后每次只需一句话触发，AI 就按照你定义的步骤、你设定的质量标准、你规划的异常处理来完成整件事。

从「每次手动提示」升级为「一次编写，反复调用」——这就是 Skills 的价值。


## 10 分钟跑通第一个 Skill

在讲原理之前，先动手。我们用 5 个步骤创建一个最简单的部署 Skill。

### 第一步：创建文件

在你的项目根目录下，创建 `.claude/skills/` 目录和文件：

```bash
mkdir -p .claude/skills
touch .claude/skills/deploy.md
```

### 第二步：写入内容

用编辑器打开 `.claude/skills/deploy.md`，写入以下内容：

```markdown
# 部署到生产环境

## 触发条件
当用户说"部署"、"deploy"、"上线"、"发布到生产"时使用。

## 前置检查
1. 确认当前在 main 分支
2. 确认没有未提交的变更（git status 干净）
3. 确认 lint 检查通过：npm run lint
4. 确认类型检查通过：npx tsc --noEmit

## 执行步骤
1. 运行构建：npm run build
2. 确认构建无报错
3. 执行部署：vercel --prod --yes
4. 等待部署完成，获取生产 URL
5. 访问生产 URL，确认页面正常加载

## 质量标准
- 构建零错误、零警告
- 部署后首页可正常访问
- 控制台无 JS 报错

## 异常处理
- 如果构建失败，输出错误信息并停止部署
- 如果部署超时，提示用户检查 Vercel 控制台
- 如果线上验证失败，提示用户回滚到上一个版本
```

### 第三步：触发 Skill

启动 Claude Code，进入你的项目目录。然后用以下任意一种方式触发：

```
# 方式一：直接输入 slash command
/deploy

# 方式二：用自然语言
帮我部署到生产环境

# 方式三：更简洁
部署
```

Claude Code 启动时会自动加载 `.claude/skills/` 目录下的所有 `.md` 文件。当你的指令匹配了 Skill 中定义的触发条件，它就会按照文档中的流程执行。

### 第四步：观察执行过程

触发后你应该看到 Claude Code 依次执行：

1. 检查当前分支 --> `git branch --show-current`
2. 检查工作区状态 --> `git status`
3. 运行 lint --> `npm run lint`
4. 运行类型检查 --> `npx tsc --noEmit`
5. 构建项目 --> `npm run build`
6. 部署 --> `vercel --prod --yes`
7. 验证线上状态

每一步都对应你在 Skill 文件中写的指令。如果某一步失败，它会按照你写的异常处理方案来应对。

### 第五步：常见失败点

如果 Skill 没有被触发，检查以下几点：

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| Claude Code 没有读取到 Skill | 文件路径不对 | 确认文件在项目根目录的 `.claude/skills/` 下，不是 `claude/skills/` |
| 触发了但执行不对 | 触发条件写得太模糊 | 在触发条件里列出明确的关键词 |
| 步骤执行顺序错乱 | 执行步骤没有编号 | 用数字编号明确顺序，不要用无序列表 |
| 失败后没有合理处理 | 缺少异常处理部分 | 补充异常处理，针对每种可能的失败场景 |
| 文件编码问题 | 文件不是 UTF-8 | 确认文件保存为 UTF-8 编码 |

到这里，你已经拥有了第一个可工作的 Skill。接下来我们拆解它的结构。


## Skill 的标准结构与设计原则

### 五个标准部分

每个 Skill 文件都应该包含以下五个部分，缺一不可：

```markdown
# 技能名称

## 触发条件
什么时候应该使用这个技能。列出具体的关键词、场景或指令。

## 前置检查
执行前需要确认的条件。不满足就不执行，避免半途失败。

## 执行步骤
按顺序列出具体操作步骤。每步一个动作，清晰明确。

## 质量标准
完成后需要满足的验收条件。怎么判断"做好了"。

## 异常处理
出现问题时的应对方案。不要让流程静默失败。
```

为什么是这五个部分？

- **触发条件**决定"何时用"。没有它，Skill 要么不会被触发，要么在不该触发时触发。
- **前置检查**是安全网。它确保执行环境就绪，避免做到一半才发现前提条件不满足。
- **执行步骤**是核心操作。必须有明确的顺序和预期结果。
- **质量标准**是验收门槛。没有它，你无法判断任务是否真正完成。
- **异常处理**是兜底方案。生产环境里，事情总会出错。

### 四个设计原则

**原则一：单一职责**

一个 Skill 只做一件事。`deploy.md` 只管部署，`review.md` 只管代码审查。不要写一个 `do-everything.md`。

为什么？因为单一职责的 Skill 更容易调试、更容易组合、更容易被正确触发。

**原则二：可组合**

好的 Skill 可以被其他 Skill 调用。比如一个 `feature-workflow.md` 可以依次调用 `write-tests.md`、`review.md`、`deploy.md`，组合成完整的功能开发流程。

要做到可组合，每个 Skill 的输入和输出要清晰，不要依赖隐式的上下文。

**原则三：可测试**

Skill 的每一步都应该有可验证的结果。不要写"确保代码质量好"，要写"lint 检查零错误，测试覆盖率不低于 80%"。

**原则四：可触发**

触发条件要具体。不要写"当需要的时候"，要写"当用户说'部署'、'deploy'、'上线'时"。关键词要和团队的日常用语对齐。

### 反例：不要这样写

**反例一：什么都做的 Skill**

```markdown
# 全能开发助手

## 触发条件
当用户有任何开发需求时使用。

## 执行步骤
1. 分析需求
2. 写代码
3. 写测试
4. 审查代码
5. 提交代码
6. 部署上线
7. 监控线上状态
```

问题：触发条件太泛，什么请求都会匹配到这个 Skill。步骤太粗，每一步都可以独立成一个 Skill。

**反例二：只有步骤没有验收**

```markdown
# 数据库迁移

## 执行步骤
1. 创建 SQL 文件
2. 写 SQL 语句
3. 执行迁移
```

问题：没有前置检查（万一连不上数据库？），没有质量标准（迁移成功的判断条件是什么？），没有异常处理（执行失败怎么办？）。

**反例三：触发条件太泛**

```markdown
## 触发条件
当用户提到代码相关的事情时使用。
```

问题："代码相关的事情"几乎涵盖了所有对话。这个 Skill 会在你不需要它的时候被触发。


## 三个完整示例

### 示例一：deploy -- 部署到生产环境（工程向）

```markdown
<!-- .claude/skills/deploy.md -->
# 部署到生产环境

## 触发条件
当用户说"部署"、"deploy"、"上线"、"发布到生产"、"推到线上"时使用。

## 前置检查
1. 确认当前在 main 分支：
   git branch --show-current
   如果不在 main，提示用户先切换分支或合并到 main
2. 确认工作区干净：
   git status
   如果有未提交的变更，提示用户先提交或暂存
3. 确认远程分支同步：
   git pull origin main
   如果有冲突，停止部署并提示解决
4. 确认 lint 检查通过：
   npm run lint
5. 确认类型检查通过：
   npx tsc --noEmit
6. 确认测试通过（如果项目有测试）：
   npm test

## 执行步骤
1. 运行生产构建：
   npm run build
   记录构建产物大小，如果比上次增长超过 20%，给出警告
2. 执行部署：
   vercel --prod --yes
   记录部署 URL 和部署 ID
3. 等待部署完成（通常 1-3 分钟）
4. 验证线上状态：
   - 访问生产 URL，确认首页正常加载
   - 检查关键 API 端点是否响应
   - 确认没有控制台错误
5. 输出部署摘要：
   - 部署 URL
   - 部署耗时
   - 构建产物大小

## 质量标准
- 构建零错误、零警告
- 部署后 30 秒内首页可正常访问
- 关键 API 返回 200 状态码
- 浏览器控制台无 JS 报错

## 异常处理
- lint 或类型检查失败：输出具体错误，不继续部署
- 构建失败：输出构建错误日志，提示开发者修复
- 部署命令失败：检查 Vercel 账号状态和网络连接
- 部署后验证失败：
  1. 输出失败详情
  2. 提示用户检查 Vercel 控制台的部署日志
  3. 建议回滚：vercel rollback
- 部署成功但页面异常：提示用户检查环境变量是否正确配置
```

### 示例二：code-review -- 代码审查（代码质量向）

```markdown
<!-- .claude/skills/code-review.md -->
# 代码审查

## 触发条件
当用户说"审查代码"、"review"、"帮我看看代码"、"代码有没有问题"时使用。

## 前置检查
1. 确认当前分支不是 main（在 main 上没有可审查的差异）
2. 确认有未合并到 main 的提交：
   git log main..HEAD --oneline
   如果没有提交，提示用户先做一些变更
3. 获取变更文件列表：
   git diff main --name-only

## 执行步骤
1. 获取完整 diff：
   git diff main
2. 按以下维度逐项审查：

   ### 安全性
   - 是否存在 SQL 注入风险（原始字符串拼接 SQL）
   - 是否存在 XSS 风险（未转义的用户输入渲染到页面）
   - 是否泄露敏感信息（硬编码密钥、API Key、密码）
   - 是否有不安全的权限检查

   ### 类型安全
   - 是否使用了 any 类型（应该用具体类型替代）
   - 是否有类型断言绕过检查（as unknown as xxx）
   - 接口定义是否完整

   ### 错误处理
   - 异步操作是否有 try-catch
   - catch 块是否只是静默吞掉错误
   - 是否有合理的用户提示

   ### 代码规范
   - 函数命名是否清晰表达意图
   - 是否有过长的函数（超过 50 行应考虑拆分）
   - 是否有重复代码可以抽取
   - 注释是否有价值（不要注释"做什么"，要注释"为什么"）

   ### 性能
   - 是否有 N+1 查询
   - 是否有不必要的重复计算
   - React 组件是否有不必要的重渲染

   ### 测试
   - 新增功能是否有对应测试
   - 测试是否覆盖了边界情况

3. 输出结构化审查报告：
   - 按严重程度分级：阻塞（必须修复）、建议（推荐修复）、提示（可以更好）
   - 每个问题标注文件名和行号
   - 每个问题给出修复建议

## 质量标准
- 审查覆盖所有变更文件
- 每个问题都有明确的严重程度和修复建议
- 不遗漏安全相关问题
- 报告可读性好，开发者看完就知道该改什么

## 异常处理
- 如果 diff 内容过大（超过 2000 行），建议分批审查
- 如果涉及二进制文件，跳过并标注
- 如果涉及第三方库的 lock 文件变更，只检查是否有可疑的依赖变化
```

### 示例三：experiment -- 科学实验流程管理（科研向 / AGI4S）

这个示例面向 AI for Science 研究者，展示 Skills 在科研场景中的应用。

```markdown
<!-- .claude/skills/experiment.md -->
# 科学实验流程管理

## 触发条件
当用户说"跑实验"、"experiment"、"开始训练"、"启动实验"、"run experiment"时使用。
当用户提供实验配置文件路径时也触发。

## 前置检查
1. 检查 GPU/NPU 可用性：
   - NVIDIA GPU：nvidia-smi，确认有空闲显存
   - 华为昇腾 Atlas 800T A2：npu-smi info，确认 NPU 可用
   如果没有可用加速卡，提示用户释放资源或排队等待

2. 检查实验配置：
   - 确认配置文件存在（通常是 config.yaml 或 config.json）
   - 验证必填字段：模型名称、数据集路径、超参数
   - 检查数据集路径是否存在且可读

3. 检查环境依赖：
   - 确认 Python 环境和必要的包已安装
   - 确认 CUDA/torch_npu 版本与硬件匹配
   - 如果使用 conda 环境，确认已激活正确的环境

4. 检查磁盘空间：
   - 确认输出目录有足够空间（至少预留模型大小 * 3 的空间）
   - 如果空间不足，提示清理旧实验或更换输出目录

5. 检查是否有同名实验正在运行：
   - 查找是否有同名进程占用 GPU
   - 如果有，提示用户确认是否要终止旧实验

## 执行步骤
1. 创建实验目录结构：
   experiments/
     {实验名}_{日期}_{时间}/
       config.yaml      # 完整配置快照
       environment.txt   # pip freeze + 系统信息
       run.log           # 训练日志
       metrics/          # 指标记录
       checkpoints/      # 模型检查点
       results/          # 最终结果

2. 记录实验元信息：
   - Git commit hash（确保实验可复现）
   - 完整的环境信息（Python 版本、包版本、CUDA 版本）
   - 硬件信息（GPU 型号、显存大小）
   - 实验配置的完整快照

3. 启动训练：
   - 使用 nohup 或 tmux 确保训练不会因终端断开而中止
   - 将日志同时输出到文件和终端
   - 启动后输出进程 PID 和日志文件路径

4. 设置监控：
   - 定期检查训练是否还在运行
   - 监控 GPU 显存和利用率
   - 如果 loss 出现 NaN，提前告警

5. 训练完成后自动整理：
   - 记录最终指标（loss、accuracy、F1 等）
   - 与基线结果对比（如果有基线）
   - 生成实验报告摘要
   - 输出关键结果

## 质量标准
- 实验配置完整可复现（另一个人拿到配置能跑出相同结果）
- 每次实验有唯一标识，不会覆盖历史结果
- 训练日志完整，可回溯任意时刻的指标
- 实验报告包含与基线的对比

## 异常处理
- GPU 显存不足（OOM）：
  1. 记录当前 batch size 和显存占用
  2. 建议减小 batch size 或使用梯度累积
  3. 保存最近的 checkpoint 以便恢复
- 训练过程中 loss 为 NaN：
  1. 记录出现 NaN 的 step 和当时的学习率
  2. 建议降低学习率或检查数据预处理
  3. 从最近的正常 checkpoint 恢复
- 训练意外中断（进程被杀/机器重启）：
  1. 检查最近的 checkpoint
  2. 提示从 checkpoint 恢复训练的命令
- 磁盘空间不足：
  1. 清理早期不需要的 checkpoint（保留最近 3 个和最优的）
  2. 压缩日志文件
```


## Skill / Tool / Hook / MCP 怎么选

这四个概念容易混淆。下面这张表帮你一眼看清它们的区别和适用场景。

### 对比总览

| 维度 | Skill | Tool | Hook | MCP |
|------|-------|------|------|-----|
| 本质 | 操作指南（Markdown） | 可执行动作（代码） | 事件触发器（配置） | 外部系统连接器（协议） |
| 形式 | `.claude/skills/*.md` | 内置或代码实现 | `.claude/settings.json` | MCP Server 配置 |
| 谁来编排 | AI 读取后自主编排 | AI 直接调用 | 系统自动触发 | AI 通过协议调用 |
| 典型粒度 | 完整流程（多步骤） | 单个操作 | 单个钩子 | 单个外部能力 |
| 触发方式 | 用户指令/关键词 | AI 自动选择 | 事件驱动（自动） | AI 需要时调用 |

### 决策指南

选择哪个，取决于你要解决的问题类型：

**场景：我要执行一个单次操作（读文件、跑命令、调 API）**
--> 用 **Tool**。Tool 是原子操作，AI 根据上下文自动选择调用。你不需要为每个基础操作写 Skill。

**场景：我有一套固定流程，每次都一样（部署、审查、迁移、跑实验）**
--> 用 **Skill**。把流程写成 Markdown，AI 读取后按步骤执行。一次编写，反复调用。

**场景：我希望某个事件发生时自动执行某个操作（保存文件后格式化、提交前检查）**
--> 用 **Hook**。在 `.claude/settings.json` 中配置事件和对应的命令，系统自动触发。

**场景：我需要连接外部系统（数据库、Slack、Jira、自定义 API）**
--> 用 **MCP**。MCP（Model Context Protocol）是标准化的外部系统连接协议，让 AI 能安全地访问外部服务。

### 组合使用

实际项目中，这四者经常组合使用：

```
用户说"部署"
  --> 触发 deploy Skill（Skill）
    --> Skill 中调用 git status、npm run build 等（Tool）
    --> 部署完成后 Hook 自动发通知（Hook）
    --> 通知发到 Slack（MCP）
```

一个好的工作流设计：
- **CLAUDE.md** 定义全局规范（"是什么"和"不做什么"）
- **Skills** 定义具体流程（"怎么做"）
- **Hooks** 处理自动化触发（"什么时候自动做"）
- **Tools** 执行具体操作（"做的每一步"）
- **MCP** 连接外部世界（"和谁对接"）


## 多 Skill 工作流

### 功能开发全流程示例

单个 Skill 解决单个任务，多个 Skill 串联可以覆盖完整的工作流。以下是一个将需求分析、编码、测试、审查、提交、部署串联起来的 Skill：

```markdown
<!-- .claude/skills/feature-workflow.md -->
# 功能开发全流程

## 触发条件
当用户提出一个新功能需求，并希望走完整开发流程时使用。
关键词："做一个功能"、"新功能"、"feature"、"从头到尾"。

## 前置检查
1. 确认当前在一个功能分支（不是 main）
2. 确认工作区干净，没有未提交的变更
3. 理解用户的需求，明确需要修改/新建哪些文件

## 工作流步骤

### 阶段 1：需求分析
1. 复述用户需求，确认理解无误
2. 列出影响范围（需要修改的文件清单）
3. 提出实现方案，包括技术选型和数据模型
4. 等待用户确认方案再继续

### 阶段 2：编码实现
1. 按照确认的方案创建/修改代码文件
2. 遵循项目现有的代码风格（参考 CLAUDE.md）
3. 添加必要的类型注解
4. 关键逻辑添加注释（说明"为什么"，而非"做什么"）

### 阶段 3：测试覆盖
（调用 write-tests Skill 的逻辑）
1. 为新增代码编写单元测试
2. 覆盖正常路径、边界条件、异常路径
3. 运行测试确认全部通过

### 阶段 4：代码自审
（调用 code-review Skill 的逻辑）
1. 按安全性、类型安全、错误处理、性能、规范逐项自查
2. 列出发现的问题和优化建议
3. 修复所有"阻塞"级别的问题

### 阶段 5：提交代码
1. git add 相关文件（不要 git add .）
2. 根据变更内容生成 Conventional Commit 格式的提交信息
3. 执行 git commit

### 阶段 6：部署（可选）
（调用 deploy Skill 的逻辑）
1. 如果用户要求部署，执行部署流程
2. 验证线上状态

## 质量标准
- 每个阶段完成后向用户确认再进入下一阶段
- 代码通过 lint 和类型检查
- 测试覆盖率不低于核心逻辑的 80%
- 提交信息准确反映变更内容

## 异常处理
- 任何阶段失败，停在当前阶段，输出失败原因
- 不要跳过失败的步骤继续执行
- 如果用户要求跳过某个阶段，记录跳过原因
```

### Hooks 配合 Skills

通过在 `.claude/settings.json` 中配置 Hooks，可以让某些操作自动触发，和 Skills 配合形成完整的质量保障链：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash(npm run build|vercel )",
        "hooks": [
          {
            "type": "command",
            "command": "npm run lint && npx tsc --noEmit"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "npx prettier --write $FILEPATH"
          }
        ]
      }
    ]
  }
}
```

这样每次编辑文件后自动格式化，每次构建或部署前自动检查——即使你忘了手动检查，Hook 也会帮你兜底。

### CLAUDE.md 与 Skills 的关系

项目根目录的 `CLAUDE.md` 是全局指令，Claude Code 每次启动都会读取。它和 Skills 的分工如下：

| 内容类型 | 放在 CLAUDE.md | 放在 Skills |
|----------|---------------|-------------|
| 项目背景和架构 | 是 | 否 |
| 全局编码规范 | 是 | 否 |
| 禁止事项 | 是 | 否 |
| 具体操作流程 | 否 | 是 |
| 部署步骤 | 否（只写一句"部署用 vercel --prod --yes"） | 是（完整的检查+部署+验证流程） |
| 技术栈信息 | 是 | 否 |

一句话总结：**CLAUDE.md 定义"是什么"和"不做什么"，Skills 定义"怎么做"**。


## AutoSkill 自动学习

### 原理

AutoSkill 是一种让 AI 从你的重复操作中自动提炼技能的机制。当你多次以相似方式完成某类任务时，Claude Code 可以识别这些模式，并自动生成 Skill 文件草稿。

它的工作流程：

1. Claude Code 观察你在会话中的操作模式
2. 识别重复出现的流程（比如你每次部署都先 lint、再 build、再 deploy）
3. 自动生成 Skill 文件草稿
4. 你审核、修改后保存到 `.claude/skills/` 目录

### 手动触发

如果你觉得刚才的操作流程值得固化为 Skill，可以在 Claude Code 中输入：

```
回顾我们刚才的对话，将其中的操作流程总结为一个 Skill 文件，
保存到 .claude/skills/ 目录下。
```

或者更具体：

```
把刚才我们做数据库迁移的流程总结为 Skill，
重点保留前置检查和回滚方案。
```

### 迭代优化

自动生成的 Skill 是起点，不是终点。你应该根据实际使用情况不断优化：

- **补充遗漏的边界情况**：第一版往往只覆盖了正常路径，用了几次后你会发现缺少的异常处理
- **删除不必要的步骤**：有些步骤在你的项目中并不需要，果断删掉
- **调整执行顺序**：实际操作中你可能发现某些步骤的顺序更合理
- **添加质量检查点**：在关键步骤后增加验证，避免错误传播到后续步骤
- **更新触发条件**：根据团队实际用语调整关键词，确保触发率

一个好的 Skill 是经过多次迭代打磨出来的，不是一次写好的。


## Skill 管理与组织

### 三个层级

Claude Code 支持三个层级的 Skill，优先级从高到低：

| 层级 | 路径 | 适用场景 | 共享范围 |
|------|------|----------|----------|
| 项目级 | `.claude/skills/` | 项目专属流程（部署、迁移） | 团队共享，跟随 Git |
| 用户级 | `~/.claude/skills/` | 个人通用习惯（Git 提交规范） | 仅个人，所有项目可用 |
| 会话级 | 对话中临时指定 | 一次性任务 | 仅当次会话 |

当同名 Skill 存在于多个层级时，项目级优先于用户级。这意味着团队可以统一流程，同时个人可以有自己的默认偏好。

### 文件组织建议

```
.claude/
  skills/
    # 工程流程
    deploy.md              # 部署到生产环境
    code-review.md         # 代码审查
    db-migration.md        # 数据库迁移
    feature-workflow.md    # 功能开发全流程

    # 代码质量
    write-tests.md         # 测试编写
    git-commit.md          # Git 提交规范
    refactor.md            # 代码重构

    # 科研场景（AGI4S）
    experiment.md          # 实验流程管理
    data-pipeline.md       # 数据预处理流水线
    benchmark.md           # 基准测试

  settings.json            # Hooks 配置
```

**文件命名规范：**

- 使用小写 kebab-case：`code-review.md`，不要用 `CodeReview.md` 或 `code_review.md`
- 名称简短明确：从文件名就能看出这个 Skill 做什么
- 每个 Skill 文件聚焦一个任务领域，不要把所有规范塞进一个文件


## 常见错误与调试

### 错误一：触发条件写得像散文

```markdown
## 触发条件
当开发者在完成一个阶段性的开发工作后，希望将代码变更保存到
版本控制系统中，以便团队其他成员可以看到最新的进展时使用。
```

问题：AI 很难从一大段描述中提取关键词。

正确写法：

```markdown
## 触发条件
当用户说"提交"、"commit"、"保存代码"、"提交代码"时使用。
```

### 错误二：执行步骤没有具体命令

```markdown
## 执行步骤
1. 检查代码质量
2. 确保测试通过
3. 部署到服务器
```

问题：每一步都太模糊，AI 不知道具体要执行什么命令。

正确写法：

```markdown
## 执行步骤
1. 运行 lint 检查：npm run lint
2. 运行类型检查：npx tsc --noEmit
3. 运行测试：npm test
4. 构建项目：npm run build
5. 部署：vercel --prod --yes
```

### 错误三：异常处理只写"联系管理员"

```markdown
## 异常处理
如果出现任何问题，请联系管理员。
```

问题：这等于没有异常处理。AI 遇到错误时无法自主应对。

正确写法：

```markdown
## 异常处理
- lint 失败：输出具体的 lint 错误，提示开发者修复后重新执行
- 构建失败：输出构建错误日志的最后 50 行，分析可能的原因
- 部署失败：检查网络连接，检查 Vercel 账号状态，输出错误信息
- 部署后验证失败：输出 HTTP 状态码和响应内容，建议回滚
```

### 错误四：质量标准不可量化

```markdown
## 质量标准
- 代码质量要好
- 性能要优秀
- 用户体验要流畅
```

问题：什么叫"好"？什么叫"优秀"？AI 无法判断是否达标。

正确写法：

```markdown
## 质量标准
- lint 检查零错误
- TypeScript 类型检查零错误
- 测试通过率 100%
- 构建产物 gzip 后不超过 500KB
- 首页加载时间不超过 3 秒
```

### 错误五：一个 Skill 文件超过 200 行

如果你的 Skill 文件写到了 200 行以上，说明它承担了太多职责。拆分它。

比如一个 200 行的 `development.md`，可以拆分为：
- `feature-analysis.md` -- 需求分析
- `write-code.md` -- 编码实现
- `write-tests.md` -- 测试编写
- `code-review.md` -- 代码审查
- `git-commit.md` -- 代码提交

然后用一个 `feature-workflow.md` 串联它们。

### 调试技巧

当 Skill 行为不符合预期时，用以下方法排查：

**1. 确认 Skill 被加载了**

在 Claude Code 中输入：

```
列出你当前加载的所有 Skills
```

如果你的 Skill 不在列表中，检查文件路径和文件名。

**2. 确认触发条件匹配了**

输入你的触发关键词后，如果 AI 没有按 Skill 流程执行，可能是触发条件不够明确。试试直接引用：

```
按照 deploy Skill 的流程执行
```

**3. 逐步调试**

告诉 AI 只执行 Skill 的某一步：

```
只执行 deploy Skill 的前置检查部分，告诉我结果
```

这样可以定位是哪一步出了问题。

**4. 查看 AI 的理解**

```
读取 .claude/skills/deploy.md 的内容，告诉我你对每个部分的理解
```

有时候问题在于 Markdown 格式不规范，导致 AI 解析出了不同的含义。
